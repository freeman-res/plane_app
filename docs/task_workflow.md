# Даты, сортировка и календарь задач

В Python API задача имеет три статуса: `todo` («Сделать»), `in_progress` («В работе»), `done` («Готово»). Её период начинается в `start_date` и, если указан срок, заканчивается в `deadline`. Приоритет: `low`, `medium`, `high`.

| Поле | При создании | Как изменить |
| --- | --- | --- |
| `start_date` | Текущая дата сервера, если не передана | Передать дату `ГГГГ-ММ-ДД` в `PATCH` |
| `deadline` | `null`, если не передана | Передать дату или `null`, чтобы убрать срок |
| `priority` | `medium`, если не передан | Передать `low`, `medium` или `high` |
| `status` | `todo`, если не передан | Передать `todo`, `in_progress` или `done` |

Дата окончания не может быть раньше даты начала. Это проверяется при создании и при частичном изменении задачи. Неверная дата, статус, приоритет или порядок дат даёт ответ 422.

## Создание и изменение

```http
POST /tasks
Content-Type: application/json

{"title":"Отчёт","start_date":"2026-12-01","deadline":"2026-12-15","priority":"high","status":"todo"}
```

`PATCH /tasks/1` принимает только меняемые поля, например `{"status":"in_progress","deadline":"2026-12-20"}`. Дату начала можно поменять одновременно с датой окончания. Для задачи без дедлайна передай `{"deadline":null}`. Ответы `POST`, `PATCH` и `GET` содержат все поля задачи.

## Сортировка

`GET /tasks` без параметров сохраняет порядок создания. Параметр `sort_by=priority` ставит сначала высокий приоритет (`high` → `medium` → `low`), а внутри приоритета — ближайший дедлайн. `sort_by=deadline` ставит сначала ближайший срок, а при равном сроке — высокий приоритет. Задачи без срока всегда в конце при сортировке по дедлайну. Параметр `descending=true` разворачивает основной порядок, но задачи без срока всё равно остаются в конце.

Те же параметры работают в папке проекта: `GET /tasks?project_id=1&sort_by=deadline` или `GET /tasks?project_id=1&sort_by=priority&descending=false`. Неверный `sort_by` отклоняется FastAPI с ответом 422. Сортировка не изменяет данные в базе.

## Данные для календаря

`GET /tasks/calendar?year=2026&month=12` возвращает дни месяца, у которых есть задачи с дедлайном. Если не передать год или месяц, берётся текущий год или месяц сервера. Для конкретного проекта добавь `project_id=1`.

```json
{
  "year": 2026,
  "month": 12,
  "days": [
    {
      "date": "2026-12-15",
      "tasks": [
        {
          "id": 1,
          "title": "Отчёт",
          "description": "",
          "project_id": null,
          "status": "todo",
          "start_date": "2026-12-01",
          "deadline": "2026-12-15",
          "priority": "high"
        }
      ]
    }
  ]
}
```

Дни без дедлайнов не включены в `days`; календарная сетка строится во Flutter. Задачи внутри дня отсортированы по приоритету. На сервере это выборка по месяцу, без изменения задач. Интерфейс Flutter в этой работе не менялся.

## Существующие задачи

При запуске `backend/database.py` добавляет `start_date` в старую SQLite-базу. Старые задачи без даты начала получают текущую дату сервера. Если сохранённый дедлайн уже прошёл, датой начала становится этот дедлайн, чтобы сохранить допустимый период. Старые задачи и проекты не удаляются. Миграция повторно не меняет уже заполненные даты.

Проверка из PowerShell в корне проекта:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

## Теги и фильтры

Задача содержит поле `tags` — список строк. При создании можно передать `{"title":"Отчёт","tags":["Учёба","Срочно"]}`; если поле не передано, список пустой. В `PATCH /tasks/{task_id}` поле `tags` заменяет прежний список целиком: `{"tags":["Учёба"]}` или `{"tags":[]}` для удаления всех тегов. Без поля `tags` старые теги не изменяются.

Имя тега обрезается по краям; пустые имена и повторы без учёта регистра не принимаются. Допускается до 20 тегов в задаче, каждый длиной до 32 символов. Поиск работает без учёта регистра и для кириллицы. Теги удалённой задачи также удаляются из базы. Отдельного справочника тегов и регистрации пользователей пока нет.

Фильтры `GET /tasks` можно сочетать между собой, с проектом и с сортировкой:

```text
GET /tasks?project_id=1&status=in_progress&priority=high&tag=учёба&sort_by=deadline
```

`status` принимает `todo`, `in_progress`, `done`; `priority` — `low`, `medium`, `high`; `tag` ищет точное имя тега без учёта регистра. Неверные значения статуса и приоритета, пустой тег и слишком длинный тег отклоняются FastAPI с ответом 422. Эти фильтры не изменяют сохранённые задачи. В `GET /tasks/calendar` теги также возвращаются вместе с задачами.

## Просроченные задачи

Если `deadline` раньше текущей даты сервера, а `status` не равен `done`, в ответе задачи поле `is_overdue` будет `true`. Дата наступления дедлайна ещё не считается просрочкой. При переносе срока в будущее или завершении задачи признак становится `false` автоматически; отдельный четвёртый статус в базе не создаётся.

`GET /tasks/overdue` возвращает просроченные задачи по ближайшему (самому раннему) дедлайну; `GET /tasks/overdue?project_id=1` возвращает их в одном проекте. Также работает фильтр `GET /tasks?overdue=true`, который можно сочетать с `project_id`, `status`, `priority`, `tag` и сортировкой. `overdue=false` возвращает остальные задачи, включая выполненные и задачи без срока.

Для карточки с `is_overdue=true` интерфейс может показать действия «Перенести срок» и «Удалить»: `PATCH /tasks/{task_id}` с новым `deadline` либо `DELETE /tasks/{task_id}`. Подтверждение удаления и выбор новой даты — элементы Flutter; бэкенд возвращает признак просрочки и поддерживает оба действия. Отдельных уведомлений при наступлении дедлайна пока нет.
