# Курсовой проект: трекер задач и проектов

Это **настольное и мобильное приложение**, а не сайт. Курсовая работа — универсальный трекер для личной работы и команды разработчиков. **AgroFlow вырастает из этого же трекера**: после курсовой к общему ядру добавятся функции для АПК. Название WorkNotes использовалось для прототипа; предмет курсовой — трекер задач и проектов.

## Принятый стек и границы проекта

- **Клиент:** один проект Flutter/Dart с приложениями для Windows и Android. Общая бизнес-логика находится в `app/lib/`; интерфейс адаптируется к размеру экрана.
- **Сервер:** Python, FastAPI, HTTP API. Он проверяет запросы и права, управляет данными и возвращает JSON.
- **Хранение:** сейчас SQLite в `backend/tasks.db`; данные остаются на сервере после перезапуска. Одна серверная база позволяет видеть одни и те же задачи на ПК и телефоне при подключении к серверу.
- **React не входит в выбранную архитектуру.** Браузерный `/docs` нужен только для проверки API и не является интерфейсом приложения.
- Для первой работающей версии нужен доступ к серверу; автономную работу без сети и последующую синхронизацию оставляем на развитие проекта.

## Что есть сейчас

Реализованы проекты и задачи, которые можно к ним привязать. В таблице `tasks` есть `id`, `title`, `description`, `status`, `project_id`, `deadline`, `priority`; статусы API: `todo`, `in_progress`, `done`. Есть таблица `projects` с `id` и `name`. Задачи пока общие: нет пользователей, команд, назначения исполнителя и проверки доступа. Базу `backend/tasks.db` с уже созданными задачами сохраняем.

| Метод и путь | Результат |
| --- | --- |
| `GET /health` | `{"status": "ok"}` — сервер работает |
| `GET /tasks` | список задач по `id`; параметр `project_id` отбирает задачи проекта |
| `POST /tasks` | создать задачу, ответ 201 |
| `PATCH /tasks/{task_id}` | изменить название, описание или статус; 404, если задачи нет |
| `DELETE /tasks/{task_id}` | удалить задачу; 204 при успехе, 404, если задачи нет |
| `GET /projects` | список проектов |
| `POST /projects` | создать проект, ответ 201 |

Текущая структура кода задач:

```text
курсач приложение/
├── backend/
│   ├── __init__.py
│   ├── main.py              # FastAPI, инициализация БД, подключение маршрутов, /health
│   ├── database.py          # таблицы и обновление старой базы
│   ├── projects/            # схемы, маршруты, сервис и SQL проектов
│   ├── tasks/
│   │   ├── schemas.py       # TaskCreate, Task, TaskUpdate: формы запросов и ответов
│   │   ├── router.py        # HTTP-маршруты и ответы 404/201/204
│   │   ├── service.py       # работа с задачами через репозиторий
│   │   └── repository.py    # SQL для чтения и изменения задач
│   └── tasks.db             # существующая база с данными
├── app/
│   ├── lib/                 # Flutter/Dart: окно задач, диалог, модель, HTTP-клиент
│   ├── pubspec.yaml         # зависимости Flutter, material_ui, http и flutter_test
│   ├── setup.ps1            # создание платформенных файлов через Flutter CLI
│   └── test/                # проверка запросов Flutter-клиента
├── frontend/                # пустая папка от прежней попытки; интерфейса сайта нет
└── README.md
```

Разбор по файлам: [`docs/task_editing.md`](docs/task_editing.md), [`docs/projects.md`](docs/projects.md) и [`docs/task_workflow.md`](docs/task_workflow.md).

Путь запроса: **Flutter → `tasks/router.py` → `tasks/service.py` → `tasks/repository.py` → SQLite → ответ JSON → Flutter**. `tasks/schemas.py` определяет допустимые поля и типы. `main.py` собирает приложение и подключает маршруты.

## Целевая архитектура курсовой

Ниже целевая структура. Задачи и базовая работа с проектами уже реализованы; пользователи, команды и заметки пока запланированы. Платформенные папки созданы Flutter CLI.

```text
курсач приложение/
├── backend/
│   ├── main.py              # сборка приложения и подключение маршрутов
│   ├── database.py          # соединение с БД и дальнейшие изменения схемы
│   ├── models.py            # таблицы пользователей, команд, проектов, задач, заметок
│   ├── routes/
│   │   ├── auth.py          # регистрация, вход, профиль
│   │   ├── teams.py         # команды, участники и роли
│   │   └── notes.py         # личные заметки
│   ├── tasks/              # код задач: схемы, маршруты, сервис, SQL
│   ├── projects/           # код проектов: схемы, маршруты, сервис, SQL
│   └── services/
│       └── permissions.py   # проверка прав на командные данные
├── app/                     # один Flutter-проект, создаётся Flutter CLI
│   ├── lib/
│   │   ├── main.dart        # точка входа
│   │   ├── app.dart         # навигация и тема
│   │   ├── core/
│   │   │   └── api_client.dart
│   │   └── features/
│   │       ├── auth/
│   │       ├── teams/
│   │       ├── projects/
│   │       ├── tasks/
│   │       └── notes/
│   ├── windows/             # создаётся Flutter
│   ├── android/             # создаётся Flutter
│   └── pubspec.yaml
├── requirements.txt         # версии зависимостей Python
├── tests/                   # проверки backend на временной SQLite-базе
└── README.md
```

Основные сущности и связи: **пользователь ↔ участие в команде → проект команды → задачи проекта**. Задача имеет название, описание, статус и впоследствии исполнителя. Для командных данных сервер должен проверять участие и роль пользователя (владелец/участник). Личные заметки принадлежат пользователю отдельно от командных задач. Статусы курсовой версии: «к выполнению», «в работе», «готово»; в API реализованы `todo`/`in_progress`/`done`, дедлайн и приоритет; элементы Flutter для их выбора добавляются отдельно.

## Порядок разработки

1. Установить Flutter SDK, выполнить `app/setup.ps1` для создания `windows/` и `android/`, загрузки зависимостей и анализа кода. Запустить окно Windows с текущим `GET /tasks`.
2. Проверить в окне создание задачи, смену статуса и удаление: код этих операций в Flutter уже написан и использует готовый API.
3. Расширить модель: пользователи, вход, команды, проекты, назначение задач, статус «в работе» и проверки прав. Изменять схему БД с сохранением существующих записей.
4. Добавить личные заметки и довести интерфейс трекера до сценариев курсовой.
5. Запустить тот же Flutter-клиент на Android и подключить его к серверу. Адрес `127.0.0.1` на телефоне обозначает сам телефон, поэтому для Android понадобится доступный ему адрес backend.
6. После курсовой развивать это ядро в AgroFlow, добавляя предметные сущности и сценарии АПК.

## Как запустить текущий backend

В терминале Visual Studio из корня `курсач приложение` при установленном локальном окружении:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --reload
```

Открыть `http://127.0.0.1:8000/docs` для проверки запросов или `http://127.0.0.1:8000/health` для проверки сервера. `/docs` показывает автоматическую документацию FastAPI; пользовательский интерфейс будет в Flutter. Если порт 8000 уже занят работающим Uvicorn, второй сервер запускать не нужно.

## Как запустить Windows-приложение

Понадобятся Flutter SDK версии не ниже 3.47 (рекомендуется актуальная стабильная версия) в `PATH` и Visual Studio с компонентом **Desktop development with C++**. В терминале из корня проекта:

```powershell
.\app\setup.ps1
cd app
flutter run -d windows
```

Скрипт `setup.ps1` запускает `flutter create` внутри существующей папки `app`, создаёт стандартные `windows/` и `android/`, затем выполняет `flutter pub get`, `flutter analyze` и `flutter test`. Исходники интерфейса лежат в `app/lib/`; их не нужно заменять стандартным примером Flutter. Для приложения на Windows FastAPI должен работать на `127.0.0.1:8000`. Для Android адрес переопределяется при запуске через `--dart-define=API_BASE_URL=http://<доступный_адрес_сервера>:8000`; настройку сети Android проверим отдельно.

Проверка backend из корня проекта: `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`. Эти тесты используют временную базу и не меняют `backend/tasks.db`. На текущем этапе реализованы только отдельные задачи; вход, команды, проекты и заметки ещё предстоит добавить.

## Договорённости по работе

- Работать в этой папке проекта. Сначала писать небольшой кусок кода и объяснять его; затем проверять вместе.
- Не подменять Flutter HTML-страницей или React-проектом. API и данные, которые уже работают, развивать постепенно.
- Не стирать `backend/tasks.db` и существующие задачи. При изменении таблиц предусматривать перенос старых данных.
- Курсовая — универсальный трекер; AgroFlow — его последующее отраслевое развитие. Это одна линия разработки, а не два несвязанных проекта.
